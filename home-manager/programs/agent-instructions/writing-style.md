# Writing Style

Applies to code comments, commit messages, PR descriptions, issue reports, and
any prose written into a repository or its tracker. The reader is a human
coming back to this code months later.

## Readable first, then concise

- Write complete sentences in prose and explanatory comments. Preserve the
  subject, verb, and causal links. Readability takes priority over saving
  words or tokens.
- Do not compress a sentence into a label, a colon, and a list of nouns.
  "Linux: toolchain, QEMU, GRUB; covers `make kernel`" saves words but makes
  the reader rebuild the sentence. Say what the reader gets and what they can
  do with it.
- Remove redundant wording while keeping the context needed to understand the
  point. Move extended detail to the commit body or documentation.
- Keep each paragraph or list item focused on one idea. Use connected prose
  to explain reasoning and lists for parallel points or steps.
- Prefer concrete facts to adjectives: "retries 3x, 200ms apart" beats
  "retries with a sensible backoff".

## No AI accent

Write like an engineer leaving a note for the next engineer, not like a chat
assistant. Avoid:

- Openers and filler: "Certainly", "Great question", "Let's dive in", "In this
  section we will", "It's worth noting that".
- Inflated adjectives: comprehensive, robust, seamless, powerful, elegant,
  production-grade, blazing-fast.
- Padding for rhythm: three-item lists where only one item is real, "not only X
  but also Y", a closing sentence that repeats the opening.
- Reflexive hedging: "generally speaking", "you may want to consider". Say it
  or drop it.
- Decoration: emoji, exclamation marks, ALL-CAPS emphasis, banner comments,
  "Generated by ..." trailers.

## Documentation

Applies to READMEs, the project book, and any page a person reads to learn a
tool rather than to review a change.

- Organize each page around its primary reader and their task. Split user
  and developer documentation when their audiences or workflows differ
  enough to make separate pages easier to use.
- Open with what the reader came for. The first paragraph says what the tool
  does for them and what they need before starting, not how it relates to
  other tools or how it is implemented.
- Order sections by the reader's timeline: prerequisites, first use,
  everyday commands, then limitations and internals.
- Include the concepts and constraints the reader needs to use or change
  the tool. Omit background that does not support that purpose.

## Comments

- Explain constraints and decisions that the code does not make clear.
  Connect necessary background to the adjacent command, flag, lock, or
  ordering instead of paraphrasing the code.
- Keep comments short, usually 1-3 lines. Use more space when needed for
  complete sentences and a clear explanation of the constraint or decision.
- Put investigation history, measurements, and detailed comparisons of
  alternatives in the commit message. Keep the context needed to understand
  the adjacent code in its comment.
- A stale comment is worse than no comment. Update comments with the code.

## PR descriptions

- Title follows the commit subject rules. Name the change, not the activity:
  `fix: drop stale SMB mount before backup`, not `Update backup handling`.
- Body answers three things and stops: what changed, why, how to verify.
- Do not narrate the diff file by file. The reviewer has the diff. Give them
  what the diff cannot show: the reason, the rejected alternative, the blast
  radius.
- Link the issue or spec rather than restating it.
- Call out what is NOT covered: skipped tests, deferred follow-ups, known gaps.
- No status theatre: no "All tests passing" banners, no checklists that repeat
  the summary, no closing thanks.

## Issues

- Title states the symptom, not a guess at the cause.
- Body: reproduction steps, expected vs actual, environment and version, and
  the relevant log or error verbatim (trimmed, not paraphrased).
- Separate what you observed from what you infer. Mark the inference as such.
- One problem per issue.
